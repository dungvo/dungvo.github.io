# Playlab Constitution

## I. Experience autonomy

Each experience owns its product promise, audience, mechanics, narrative and evidence of success. Do not copy assumptions between experiences without an explicit shared decision.

## II. Consistent, legible systems

Given the same relevant world state, the same action produces the same result unless randomness is explicitly signaled. Feedback must let a child form, test, and revise a hypothesis.

## III. Purpose before abstraction

Build shared infrastructure only for demonstrated cross-experience needs. Prefer the smallest design that serves the current accepted spec.

## IV. Safe, accessible and audience-aware

Every experience explicitly defines its audience, accessibility, safety and privacy boundaries; Playlab does not assume all experiences target the same age or learning goal.

## V. Spec and evidence before implementation

Design/specification precedes code. A feature needs acceptance criteria and a playtest/learning-observation plan. Observed behavior is evidence; completion alone is not proof of learning.

## VI. Minimal architecture

Architecture is decided per experience. Login, cloud services, analytics, shared engines and deployment pipelines are never inherited implicitly.

## VII. Human authority and traceable decisions

AI may analyze and propose, but the owner decides product promise, major mechanics, learning scope, data/privacy, dependency direction, implementation, acceptance and release. Decisions are recorded as `DEC-*`; rejected and superseded decisions remain traceable.

## Governance

`docs/decision-log.md` records Playlab-wide decisions; each experience has its own decision log. Amendments require reason, affected artifacts and owner acceptance. Conflicts are resolved in this order: explicit current owner decision → constitution → accepted spec → design docs → proposals/backlog.
